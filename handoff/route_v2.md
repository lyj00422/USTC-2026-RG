# Route v2 当前交接入口

当前自动化程序采用库存/槽位驱动循环。完整说明见同目录 `交接文档.md`。

**当前版本：`预赛_完美版`（2026-09-30，`4d33d60`，tag 同名并已推远端）之上，2026-10-01 现场又改了一处（未打 tag、未提交）：搭建区定位由视觉改成纯里程。** 上一版 `预赛_半完美版`（同日，无 tag）——恢复现场时先看 `交接文档.md` 顶部那几节，它们才是"这版和上一版差在哪"。

**搭建区定位 = 纯里程（2026-10-01）。** 第 N 栋（放置）／封顶第 N 栋 = **进搭建区那个位姿往右 `5 × N` cm**：
`build_right_step_cm`（默认 **5.0**）——第1栋5cm、第2栋10cm、第3栋15cm，封顶第1栋5cm、第2栋10cm。
判定完全不看视觉（`offset = step × (skip + 1)`，`skip` 就是原来的 `building_count` / `cap_count`）。
原来那套 `BUILD_OCCUPANCY` 视觉判定（数方块出视野 + 封顶对准）**整体注释掉了、没有删**，
`state_machine.py` 的 `BUILD_AREA` 里有一整段标注了恢复方法；**搭建区现在不选任何视觉任务**，
所以相机在那一段挂掉不会再把整趟拖进 FAULT。细节与改动理由见 `交接文档.md` 顶部那节。

关键约束：紫色固定左槽且最多一个；车辆最多三个方块；橙色动作完成后直接再次识别，不追加 `D20`；搭建后倒车 30 cm、左旋 180°；有紫色直接走 330 cm 那条腿到取物区 1（**巡线**，`direct_orange_distance_cm` 只是里程闸门），无紫色复用 J2 到 J3 判断并检查紫色；`SUCTION,true` 保持到明确的 `SUCTION,false`；仅当紫色和橙色都识别不到时停止。

**第 3 栋（最后一栋）全橙（2026-10-02）。** 出搭建区时若 `loop_context.building_count >= 2`（已有两栋站着 → 下一栋就是第 3 栋），直接走 330 cm 那条腿到取物区 1、**跳过 J2/J3 和整个紫色区**（`loop_strategy.all_orange_round`，分岔在 `state_machine.py` 的 `BUILD_TURN_SEEK_LINE`）。车到取物区 1 时是**空车**，三个槽全装橙，搭建计划是 `BUILD_3`（`build_three` 包「从吸盘右侧左侧搭建三个橙色」），搭建位 = `build_first_right_cm + build_right_step_cm × 2`。第 1、2 栋照旧 1 紫 + 2 橙 → `BUILD_BASE` + `PLACE_PURPLE`；第 3 栋不再去紫色区，**第三个紫色留在原地**。第 3 栋搭完程序不会自己停（和以前一样会继续下一轮）。

**路线自己的腿段**基本都是 80，**唯一例外是 `pickup_3_speed: 50`**——只给取物区1 → 搭建区那条腿（`JUNCTION_PICKUP_3_TO_AREA`）；反方向那条仍是 80，两条腿形状一样、只能靠方向分。**动作包不是**——包里的速度是自带值（抓取包 `v`/`D` 都是 20，搭建包沿用录制值），`forward_speed_limit: 80` 只是编译期对正 `vx` 的截断上限。别把包提速到 80 当成"改成标准值"。

**抓取时下一个橙块放进哪个槽 = 右槽 → 吸盘槽 → 左槽**（左槽固定紫块、留到最后封顶），由 `loop_strategy.next_orange_slot` 决定，包本身不判断。这只是三个顺序里的一个：**封顶时优先用哪一槽的橙**是吸盘槽 → 右槽（`build_plan_for_inventory`），**搭底层用的是**吸盘槽的橙 + 右槽的橙。别把它们混成一个。角色→包→层那张表见 `交接文档.md`「搭建动作」。

**舵机基准（2026-09-29 部署版，不是"当前值"）**：复位 id0 1840 / id1 1520 / id2 1500 / id3 1400；抓左槽 id0 **630**、抓右槽 id0 **1020**。id4 存在但从未被动作包使用。包不在仓库里、id-0 那几个位姿是手工调的，**重新部署会覆盖掉现场值**——部署前先在 Pi 上读当前值对比。

**找线接受度 `seek_line_min_black_probes` 现在是 4**（2026-09-30 由 1 改回）。这是个**两头都会坏**的旋钮：调高到 4 是修 `BUILD_BACK_TO_LINE`（1 的时候任意一道探头擦到线就算"已在线"，左移找线分支根本进不去），调回 1 是修"找不到线"。现场报症状时先确认是哪一头。

⚠ **跑之前必须做**：抓取包里有 `D -12/-17/-15/-16 0 0 20`，而全仓库从无负 `forward_cm` 先例——**轮子离地先单发一条 `D -17 0 0 20` 确认是后退**，符号反了会顶进墙。另外 `D` **不能重发**（固件会重启移动，STOP 幂等、`D` 不幂等）。

底盘链路：保活由 `rg_runtime/chassis_link.py` 的 `ChassisLink` 负责，端口一打开就起心跳线程，
与 tick 无关（2026-09-29 重构，之前保活写在 tick 里，覆盖不到运行开头 20–40 秒的初始化静默——
存档 60 次运行的 10 次掉线全部落在运行前 90 秒）。参数 `chassis_heartbeat_*` 见 `config/route_v2.yaml`。

⚠ **回线这一块 2026-09-30 连修两处，别再按旧说法排查**（细节见 `交接文档.md`「取物后回线」「回线故障」）：

- 橙区回线的方向原点**每次进区只锁存一次**。之前绑在"task 变化"上，而动作包每抓一次就让 tick 重新选中那个 task，原点被挪到**最后一次抓取之后**的位姿，净横移恒读到 0 或负数 → 车朝着**取块来过的方向**找线（run `20260930_164742` 第 4 轮：net −1.5，往左 78 cm 撞上界 fault）。**方向推错先查这个原点，不是摇摆兜底。**
- 单向/摇摆搜索耗尽**不再原地 fault**：先开回进区那个位姿（`center_cm`，实测那里线阵读 `mask 0` = 线所在），到位后才把「照常去搭建区」的结果交给状态机；回程本身就是一次找线，读到线即算成功。
- `PICKUP_2_RETURN_TO_LINE` 的 fault **已经**映射到 `PICKUP_2_RETURN`（半完美版）——静默保持结束了。`PURPLE_RETURN_TO_LINE` 仍然 fault → `FAULT` 状态，那是有意的。
- 仍然成立：**`FAULT` 状态本身也是原地 STOP 保持**，不重试、不退出。所以"车不动"不区分"在等"和"已放弃"——看 `state` / `pickup_phase` / `FAULT_SAFE` 三行。

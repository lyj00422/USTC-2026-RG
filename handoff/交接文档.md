**橙区回线的方向原点（`run_route_v2.py`）**

原点的锁存键从「task 变化」改成「**每次进入取物区只锁存一次**」（`_orange_origin_state`）。
动作包每抓一次就 suspend 掉 `ORANGE_CLOSE`，下一拍 tick 又重新选中它，于是原点被重置到
**最后一次抓取之后**那个位姿——也就是搜索的远端。net 因此读到 0 或负数，
`_orange_return_direction` 把车朝取块来的方向送出去。第 4 轮：原点 172.48、回线 170.96、
net **−1.5** → 往左一路到 78 cm 撞上界 fault。

**搜索耗尽先回中（`route_v2/pickup_vision.py`）**

`PickupReturnController` 新增 `center_cm` 与 `return_guard_margin_cm`。单向/摇摆搜索耗尽时
**不再原地 fault**，而是先开回**进区那个位姿**——实测那里线阵读 `mask 0`（黑线所在），
而搜索腿经过的 120–250 cm 全是 255。到位后才把状态机那个「照常去搭建区」的结果交出去；
回程本身就是一次找线，探头读到线即算成功（`probe_line_confirmed`），不必走到死推算的那个数。
回程有界：要走的距离加 `return_guard_margin_cm`（各取物区自己的 `return_guard_margin_cm`，
默认 15 cm），以及超时；走完仍没读到线才 fault。

**控制台（`control_hub/services/chassis_service.py`）**

`open_retry_interval_s` 2.5 s）。2026-09-30 重启后 auto-connect 撞上 `[Errno 5]`，而链路

## 库存与路线

车辆最多携带三个方块，库存固定为 `left_slot`、`right_slot`、`suction_slot`。紫色最多一个且固定左槽；无紫色时橙色按左、右、吸盘装载；有紫色时橙色按右、吸盘装载。

首轮取一紫二橙到搭建区，先搭两层橙色，紫色留车上。每次搭建完成后倒车 30 cm、左旋 180°，沿线复用 J2 到 J3 的到达判断。J3 需要紫色时走现有紫色取物路线；紫色已经在车上时跳过 J3 判断，直接走搭建区 → 取物区1 那条腿（`direct_orange_distance_cm: 330` 只是**里程闸门**，**2026-09-24 起这条腿是巡线，不是盲走 `D`**）。

取橙色固定执行“识别、对中、抓取、再次识别”。动作包负责对应槽位抓取和释放；动作完成后不追加 `D20`。容量未满且识别到橙色就继续取；识别不到橙色才回搭建区。

## 搭建动作

搭建区先识别已有两层橙色的状态。这里有**三个不同的顺序**，之前把它们混成了一个，读代码时别再看错：

| 什么时候 | 顺序 | 在哪 |
|---|---|---|
| **抓取时，下一个橙块放进哪个槽** | 右槽 → 吸盘槽 → 左槽 | `LoopContext.next_orange_slot` |
| **封顶时，优先用哪一槽的橙** | 吸盘槽 → 右槽 | `build_plan_for_inventory:180-183` |
| **恢复槽位状态时按什么装载** | 无紫：左 → 右 → 吸盘；有紫：右 → 吸盘 | `LoopContext.__post_init__` |

左槽始终留给紫块、放到最后封顶。搭底层实际用的是**吸盘槽的橙 + 右槽的橙**——`loop_strategy.py:186-187` 的注释写明 `0007` 就是「放吸盘的橙色和右边的橙色作为两层」。旧包自己的 `id0` 序列一律右槽 `1900`、左槽 `1520`（新基准 `1020` / `630`）。

首轮使用两层橙色动作；已有两层橙色时，只有紫色执行封顶，带橙色和紫色时先放橙色再放紫色。无紫色时按橙色数量执行三层、两层或单块放置。没有动作包的组合统一用 `复位_final` 占位。

## 吸盘锁存

`SUCTION,true` 一旦执行就保持吸附。动作包完成、复位占位、动作切换、巡线和转弯均不得隐式释放；只有明确的 `SUCTION,false` 才能关闭。当前动作包角色与路径由 `runtime/data/route_v2_actions/catalog.json` 管理。

**吸盘保活（2026-09-30 起，`arm_suction_hold_period_s: 2.0`）。** 路线只在动作包的某一步等
ack 时才跟机械臂说话，所以**举着方块跑去搭建区那几分钟里机械臂收不到任何指令**——吸住是
抓取包做的，之后没人再确认过它，掉了也没人知道。这和底盘那条「空闲拆链」是同一类暴露面，
是它的机械臂版本。保活**只在没有动作包运行时**补发：动作包自己的 `SUCTION` 步在等 ack，
一条来路不明的 ack 绝不能替它完成那一步，尤其不能替一条**放吸**命令完成（那会让释放根本
没发出去而程序继续往下走）。`0` = 关闭，退回 2026-09-29 之前的行为。

### 两种移动步

```json
{"kind":"CHASSIS","command":"velocity","vx":20,"vy":0,"wz":0}
{"kind":"CHASSIS","command":"distance","forward_cm":-17,"right_cm":0,"rotate_deg":0,"speed":20}
```

- `velocity` **后面必须紧跟一条 `stop`**，编译器把两者合并成一个定时移动（时长 = 两条的时间戳之差）。
- `distance` 由固件的 `D` 命令闭环完成：执行器**发一次，然后等固件回 `DONE`**。**绝不重发**——固件会**重启**一个重发的 `D`（STOP 幂等，`D` 不幂等），重试会让车把这段路再走一遍。下发时路线会清掉 `DONE` 闩锁，避免上一条的残留结算这一条。**2026-09-30 起**等不到 `DONE` 的处置改了：`distance_timeout_s` 由 30 收到 **10**（`pickup_action.py` 的构造默认值，不在 yaml 里），且**不再 fault 整趟**，而是跳过该步继续，遥测里计 `distance_timeouts` 并打印一行 `ACTION D … reported no DONE`。丢一条 `D` 是现场反复出现的现象（`PICK_ORANGE_RIGHT` 里反复丢 `D -15` / `D 3`），让它报废整趟代价太大。
- **抓取包（紫/橙×4）用 `distance`，搭建包仍用 `velocity`**（按现场要求搭建包未改）。

### 动作里的停顿（2026-09-30 起，`catalog.json` 驱动）

## 速度与停止

**路线自己的腿段**基本都是 80：巡线、转场、转向、取物区路径上限均为 80（`pickup_speed: 80` /
`turn_speed: 80`）。**唯一的例外是 `JUNCTION_PICKUP_3_TO_AREA`（取物区1 → 搭建区）那条腿，
`pickup_3_speed: 50`**——操作员 2026-09-29：「这个前进速度是50 但是这是取物区到搭建区的速度
然后搭建区前往取物还是80」。反方向那条（搭建区 → 取物区1，`direct_orange_distance_cm`）保持
80。**这两条腿形状一模一样（都是倒车 → 旋转 → 前进），只能靠行进方向分**，改速度时别看错
是哪一条——2026-09-29 那次 50 就先被放到了反方向那条上。

**动作包不走这条路**：包里的速度是**录制/指定时自带的值**——抓取包的 `v` 步是 `±20`、`D` 步是 `speed 20`，搭建包沿用录制的 `±20`。`forward_speed_limit: 80` 只是编译期对**正的 `vx`** 的截断上限，不是包的实际速度。调试时不要以为把包提速到 80 是"改成标准值"。

唯一业务停止条件是：J3 识别不到紫色并且取物区 1 识别不到橙色。满载、单次无目标、完成搭建或紫色封顶都不能单独停止。

## 取物后回线

取物完成后重新找线由 `runtime/route_v2/pickup_vision.py` 的 `PickupReturnController` 执行，方向在构造控制器时定下，分两条路：

- **单向回线（主逻辑）**：方向从**进区之后的净横移**反推。紫色区用预扫描槽位（`{1: -1, 3: 1}`）；橙色区用 `run_route_v2.py` 的 `_orange_search_origin_cm`——**每次进入取物区只锁存一次**的进区位姿，`net = 当前横坐标 − 进区横坐标`，`_orange_return_direction(net)` 让车朝**净移动的反方向**开回去找线；只有 `net == 0`（一次横移都没见过）才落到摇摆兜底。横向额度取该取物区**自己实测的安全横移距离**（橙色用 `search_left` / `search_right` 的 `max_distance_cm`，两个方向各 75 cm、独立标定；紫色区仍用 `seek_line_max_cm`）。
- **递增摇摆（兜底）**：只在方向推不出来时使用（`one_way == 0`），幅度由 `pickup_return_line_swing_cm` 给出。

两条路每一拍都用 `seek_line_confirm_frames` 判是否找到线。

**⚠ 2026-09-30 修正：原点的锁存键错了，不是「没有第二道保险」。**

在那之前原点是绑在「task 变化」上的，而动作包每抓一次就 suspend 掉 `ORANGE_CLOSE`、下一拍
tick 又重新选中它——原点因此被重置到**最后一次抓取之后**那个位姿（搜索的远端），净横移恒
读到 0 或负数，车就朝着取块来过的方向找线。run `20260930_164742` 第 4 轮：原点 172.48、
回线 170.96、net **−1.5** → 往左一路横移到 78 cm 撞上界 fault；第 2、3 轮只是锁存位姿碰巧
离得远才蒙对。现在原点只随「进入取物区」这一次事件移动。**方向推错时先查的是这个原点，
不是摇摆兜底。**

**搜索耗尽的收尾（`center_cm` + `return_guard_margin_cm`，2026-09-30 起）。**

单向/摇摆两条路都走完还没读到线时，控制器**先开回进区那个位姿**（`center_cm`，实测那里线阵
读 `mask 0` = 黑线所在，而搜索腿经过的 120–250 cm 全是 255），到位后才把结果交给状态机。
两条理由：回程本身就是一次找线，探头读到线即算成功（`probe_line_confirmed`），不必走到死
推算的那个数；而紧接着的倒车+旋转是**故意不靠传感器**的，在横移出去 78 cm 的地方起步会把
整个横向误差带进那条腿。回程有界：要走的距离加 `return_guard_margin_cm`（各取物区自己的
`return_guard_margin_cm`，默认 15 cm），以及超时；走完仍没读到线才 fault。
紫色区 `center_cm` 为 `None`，保持原样（它的 fault 本来就直接进 FAULT 状态）。

## 找线的掩码判据

`run_route_v2.py` 的 `_line_found` 是唯一判据，**置位是白、清零才是黑**：

```
probes = 8 - popcount(mask)
line_found = mask in seek_line_masks or (seek_line_min_black_probes <= probes < 8)
```

当前 **`seek_line_min_black_probes: 4`**（2026-09-30 由 1 改回，理由见「预赛_半完美版」一节的表）。
这是个**两头都会坏**的旋钮：4 是修 `BUILD_BACK_TO_LINE`（1 的时候任意一道探头擦到线就算「已在线上」，左移找线分支根本进不去），1 是修「永远找不到线」。现场报症状时先确认是哪一头。

`probes == 8`（全黑 `0x00`）与 `probes == 0`（全白 `0xFF`）**都不接受**。
`rg_runtime/line_sensor.py` 里 `lost = (压黑路数 == 0)`，所以 **`mask == 0xFF` ⟺ 一路探头都没压黑 ⟺ `line_error is None`**。遥测里读到 `mask: 255, line_error: null`，含义是「车底下没有线」，**不是**线阵掉线——`line_error` 为 None 正是丢线的正常伴随值，两者不是两个独立信号。

## 回线故障：静默保持已修（2026-09-30）

`PICKUP_2_RETURN_TO_LINE` 原来**没有** `pickup_kind == "fault"` 分支，fault 会落进 `else`
返回 `stop`：原地发 STOP 无限保持，不重试、不退出，只有 `--timeout-s` 或人工 kill 能结束。
**`预赛_半完美版`（`9484398`）补上了这个分支，映射到 `PICKUP_2_RETURN`——照常去搭建区。**


## 蓝牙链路重构（2026-09-29）

把保活从"状态机的副产品"变成"链路自身的保证"。新增 `runtime/rg_runtime/chassis_link.py`
的 `ChassisLink`，收口这条链路的全部所有权：端口锁、transport、心跳、重连。

### 为什么改

不是射频问题，是**结构性静默窗口**。`run_route_v2.py` 在函数最顶部就开端口并 `STOP` 预热，
之后才是线阵（`startup_delay_s: 20`）、摄像头、机械臂、动作包编译。这段 20–40 秒里总线上
一个字节都没有，而 JDY-31 空闲 13–20 秒即拆 SPP 会话。

存档 60 次运行（2026-09-15～29）实测：**10 次掉线全部落在运行前 90 秒内**，三次最长的
（22.5 / 20.4 / 18.2 秒）落在 23.0 / 25.4 / 27.2 秒——正是第一个 tick 第一次碰底盘的时刻。
控制台从来没有这个问题，因为它的保活是 `control_hub/server.py:262` 的独立循环，端口一打开
就在跑；路线的保活写在 tick 里（`if issued is None and not action_owns_chassis:`），
**在第一个 tick 之前根本不存在**。

### 改了什么

- 心跳是 `ChassisLink` 自己的守护线程，**`open()` 时就启动**，与路线控制流无关。
- 心跳逻辑是同步方法 `heartbeat_tick(now)`，线程只是薄驱动——项目既有测试范式是
  「同步 tick + 注入假时钟」，这样全部逻辑都可单测。
- **quiet 窗口避让**（默认 2 秒，照抄控制台已验证的值）：固件只回答连发命令里的第一条，
  保活压在运动命令上会把那条 `V` 吞掉，车不动，表现得和机器人死了一模一样。
- 一把 `RLock` 串行化全部串口访问，并在**同一把锁内**原子地做「检查空闲 → 发送 → 更新
  `last_tx`」，防止心跳与 tick 交错。
- 重连搬进 `ChassisLink.recover()`，返回 `self`（运行循环会 `self.chassis = recover(...)`，
  而这个对象就是那个句柄）。
- **自证诊断**：重连时打印 `last byte on the wire N s before the error`。N 落在 13–20 秒
  即证明是空闲拆链（心跳能治）；N 明显更短说明会话是在**正在通信时**死的——那要看供电，
  不是看保活。

### 参数（`config/route_v2.yaml`）

| 参数 | 默认 | 说明 |
|---|---|---|
| `chassis_heartbeat_enabled` | `true` | 改 `false` 退回重构前行为做 A/B |
| `chassis_heartbeat_s` | `5.0` | 与控制台 `keepalive_s` 同值 |
| `chassis_heartbeat_quiet_s` | `2.0` | 必须短于 `chassis_heartbeat_s`，校验强制 |

tick 里那段 0.15 秒的 ENC/SPD 快速查询**不是保活，是传感**（J1 触发与接触段靠它做里程
门限），保持原样。

### 没修的

**共电源压降。** 保活能防对端空闲超时，防不了对端掉电。`TAG_2_TURN_RIGHT` 上那两次
（运行第 66.0 / 82.3 秒）超出启动窗口，更像大电流转向时底盘侧被拉垮——其中一次恢复后
固件报回的编码器计数从 `-2776` 回到 `-86`，而路线程序从不调用 `reset_encoder`。这需要
示波器在"70+ 速度原地转向 + 机械臂同时动作"时测轨压，软件修不了。

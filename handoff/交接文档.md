### 本版存在、并已在下方「蓝牙链路重构」修复的两个缺口

1. **启动段有 20–40 秒的底盘静默。** `run_route_v2.py:2012` 只发一次 `STOP` 预热，之后是
   线阵 `startup_delay_s: 20` 的稳定期加摄像头/机械臂/动作包初始化，全程不与底盘通信。
   JDY-31 空闲 13–20 秒即拆会话，所以路线常常在真正开跑前就丢了链路。
   控制台没有这个窗口——它的保活是 `server.py:262` 的独立循环，端口一打开就在跑。
2. **保活被 tick 门控。** `run_route_v2.py:1411` 的 `if issued is None and not
   action_owns_chassis:` 使保活在启动段和动作包接管期整段失效；保活只存在于第一个 tick
   之后，而丢会话恰恰发生在第一个 tick 之前。

`预赛_v1` 标签冻结的是**修之前**的状态，可随时回退对比。

## 库存与路线

车辆最多携带三个方块，库存固定为 `left_slot`、`right_slot`、`suction_slot`。紫色最多一个且固定左槽；无紫色时橙色按左、右、吸盘装载；有紫色时橙色按右、吸盘装载。

首轮取一紫二橙到搭建区，先搭两层橙色，紫色留车上。每次搭建完成后倒车 30 cm、左旋 180°，沿线复用 J2 到 J3 的到达判断。J3 需要紫色时走现有紫色取物路线；紫色已经在车上时跳过 J3 判断，直接执行 `D330` 到取物区 1。

取橙色固定执行“识别、对中、抓取、再次识别”。动作包负责对应槽位抓取和释放；动作完成后不追加 `D20`。容量未满且识别到橙色就继续取；识别不到橙色才回搭建区。

## 搭建动作

搭建区先识别已有两层橙色的状态。**方块取用顺序始终是吸盘槽 → 右槽 → 左槽**（左槽固定紫块，留到最后封顶）。这个顺序不是约定，而是被三处独立证据锁定的：`loop_strategy.py:186-187` 的注释写明 `0007` 是「放吸盘的橙色和右边的橙色作为两层」；`build_plan_for_inventory` 的触发条件决定每个包的到货状态；旧包自己的 `id0` 序列一律右槽 `1900`、左槽 `1520`（新基准 `1020` / `630`）。

首轮使用两层橙色动作；已有两层橙色时，只有紫色执行封顶，带橙色和紫色时先放橙色再放紫色。无紫色时按橙色数量执行三层、两层或单块放置。没有动作包的组合统一用 `复位_final` 占位。

## 动作包（2026-09-29 部署版）

### 文件与角色

包在 `runtime/data/route_v2_actions/<role>_latest/`，角色 → 路径由同目录 `catalog.json` 绑定（13 个角色指向 12 个包，`cap_purple` 与 `place_purple` 同一个）。路线**只读 `action.json` + `zones.json`**；包里的 `arm.json` / `camera.jpg` / `chassis.json` / `metadata.json` 是控制台的录制素材，路线不读。

`.gitignore` 的 `data/` 规则把 `runtime/data/` 整个忽略了，所以**动作包不在代码仓库里，是现场数据**——重建/部署走 `pi-tools/_pi_push_files.py`。

**抓取窗口与视觉识别沿用自动化程序自己的配置**，不来自动作包：包里的 `zones` 只用于和 `action.json` 的 `zones` 字段比对一致性、以及 `require_capture_window` 门禁，而 catalog 里**每个角色都是 `window_required: false`**，门禁从不触发。真正的窗口在 `pickup_vision.py` 读 `self.profile.capture_window`。

### 两种移动步

```json
{"kind":"CHASSIS","command":"velocity","vx":20,"vy":0,"wz":0}
{"kind":"CHASSIS","command":"distance","forward_cm":-17,"right_cm":0,"rotate_deg":0,"speed":20}
```

- `velocity` **后面必须紧跟一条 `stop`**，编译器把两者合并成一个定时移动（时长 = 两条的时间戳之差）。
- `distance` 由固件的 `D` 命令闭环完成：执行器**发一次，然后等固件回 `DONE`**，等不到就 fault。**绝不重发**——固件会**重启**一个重发的 `D`（STOP 幂等，`D` 不幂等），重试会让车把这段路再走一遍。下发时路线会清掉 `DONE` 闩锁，避免上一条的残留结算这一条。
- **抓取包（紫/橙×4）用 `distance`，搭建包仍用 `velocity`**（按现场要求搭建包未改）。

数字从左到右 = 舵机 id 0→3；下发顺序沿用旧录制的实际顺序（**不是**严格降序）。

| 项 | 值 |

| 抓左槽 | id0 → **630** |
| 抓右槽 | id0 → **1020** |

## 速度与停止

**路线自己的腿段**统一 fast80：巡线、转场、转向、取物区路径上限均为 80。

**动作包不走这条路**：包里的速度是**录制/指定时自带的值**——抓取包的 `v` 步是 `±20`、`D` 步是 `speed 20`，搭建包沿用录制的 `±20`。`forward_speed_limit: 80` 只是编译期对**正的 `vx`** 的截断上限，不是包的实际速度。调试时不要以为把包提速到 80 是"改成标准值"。

唯一业务停止条件是：J3 识别不到紫色并且取物区 1 识别不到橙色。满载、单次无目标、完成搭建或紫色封顶都不能单独停止。

## 取物后回线

取物完成后重新找线由 `runtime/route_v2/pickup_vision.py` 的 `PickupReturnController` 执行，方向在 J3 判定，分两条路：

- **单向回线（主逻辑）**：方向从取物过程本身反推。紫色区用预扫描槽位（`{1: -1, 3: 1}`）；橙色区用 `run_route_v2.py` 的 `_last_pickup_lateral`——车朝哪边开过去取块，回线就往反方向找（`one_way = -_last_pickup_lateral`）。横向额度取该取物区**自己实测的安全横移距离**（橙色用 `search_left` / `search_right` 的 `max_distance_cm`；紫色区仍用 `seek_line_max_cm`）。
- **递增摇摆（兜底）**：只在方向推不出来时使用（一次横向命令都没见过，`one_way == 0`），幅度由 `pickup_return_line_swing_cm` 给出。

两条路每一拍都用 `seek_line_confirm_frames` 判是否找到线。

**⚠ 单向分支没有第二道保险。** 方向一旦推得出来就走单向，永远不会落到摇摆兜底；方向推错或额度不够，结果直接就是 FAULT。

## 找线的掩码判据

`run_route_v2.py` 的 `_line_found` 是唯一判据，**置位是白、清零才是黑**：

```
probes = 8 - popcount(mask)
line_found = mask in seek_line_masks or (seek_line_min_black_probes <= probes < 8)
```

`probes == 8`（全黑 `0x00`）与 `probes == 0`（全白 `0xFF`）**都不接受**。
`rg_runtime/line_sensor.py` 里 `lost = (压黑路数 == 0)`，所以 **`mask == 0xFF` ⟺ 一路探头都没压黑 ⟺ `line_error is None`**。遥测里读到 `mask: 255, line_error: null`，含义是「车底下没有线」，**不是**线阵掉线——`line_error` 为 None 正是丢线的正常伴随值，两者不是两个独立信号。

## 回线故障是静默保持

`PICKUP_2_RETURN_TO_LINE` **没有** `pickup_kind == "fault"` 分支，fault 会落进 `else` 返回 `stop`：原地发 STOP 无限保持，不重试、不退出，只有 `--timeout-s` 或人工 kill 能结束。

对照 `PURPLE_RETURN_TO_LINE`，它有：

```python
if visual.pickup_kind == "fault":
    self._enter(RouteState.FAULT, now)
```

其注释写明理由：「Fault rather than hold: a silent hold is indistinguishable from a hang on the field」。同一条理由对 `PICKUP_2_RETURN_TO_LINE` 没有落实。`PICKUP_2_VISION_ONLY` 与 `BUILD_ACTION` 都有这个映射，**缺的只有 `PICKUP_2_RETURN_TO_LINE`**。

## 蓝牙链路重构（2026-09-29）

把保活从"状态机的副产品"变成"链路自身的保证"。新增 `runtime/rg_runtime/chassis_link.py`
的 `ChassisLink`，收口这条链路的全部所有权：端口锁、transport、心跳、重连。

### 为什么改

不是射频问题，是**结构性静默窗口**。`run_route_v2.py` 在函数最顶部就开端口并 `STOP` 预热，
之后才是线阵（`startup_delay_s: 20`）、摄像头、机械臂、动作包编译。这段 20–40 秒里总线上
一个字节都没有，而 JDY-31 空闲 13–20 秒即拆 SPP 会话。

存档 60 次运行（2026-09-15～29）实测：**10 次掉线全部落在运行前 90 秒内**，三次最长的
（22.5 / 20.4 / 18.2 秒）落在 23.0 / 25.4 / 27.2 秒——正是第一个 tick 第一次碰底盘的时刻。
控制台从来没有这个问题，因为它的保活是 `control_hub/server.py:262` 的独立循环，端口一打开
就在跑；路线的保活写在 tick 里（`if issued is None and not action_owns_chassis:`），
**在第一个 tick 之前根本不存在**。

### 改了什么

- 心跳是 `ChassisLink` 自己的守护线程，**`open()` 时就启动**，与路线控制流无关。
- 心跳逻辑是同步方法 `heartbeat_tick(now)`，线程只是薄驱动——项目既有测试范式是
  「同步 tick + 注入假时钟」，这样全部逻辑都可单测。
- **quiet 窗口避让**（默认 2 秒，照抄控制台已验证的值）：固件只回答连发命令里的第一条，
  保活压在运动命令上会把那条 `V` 吞掉，车不动，表现得和机器人死了一模一样。
- 一把 `RLock` 串行化全部串口访问，并在**同一把锁内**原子地做「检查空闲 → 发送 → 更新
  `last_tx`」，防止心跳与 tick 交错。
- 重连搬进 `ChassisLink.recover()`，返回 `self`（运行循环会 `self.chassis = recover(...)`，
  而这个对象就是那个句柄）。
- **自证诊断**：重连时打印 `last byte on the wire N s before the error`。N 落在 13–20 秒
  即证明是空闲拆链（心跳能治）；N 明显更短说明会话是在**正在通信时**死的——那要看供电，
  不是看保活。

### 参数（`config/route_v2.yaml`）

| 参数 | 默认 | 说明 |
|---|---|---|
| `chassis_heartbeat_enabled` | `true` | 改 `false` 退回重构前行为做 A/B |
| `chassis_heartbeat_s` | `5.0` | 与控制台 `keepalive_s` 同值 |
| `chassis_heartbeat_quiet_s` | `2.0` | 必须短于 `chassis_heartbeat_s`，校验强制 |

tick 里那段 0.15 秒的 ENC/SPD 快速查询**不是保活，是传感**（J1 触发与接触段靠它做里程
门限），保持原样。

### 没修的

**共电源压降。** 保活能防对端空闲超时，防不了对端掉电。`TAG_2_TURN_RIGHT` 上那两次
（运行第 66.0 / 82.3 秒）超出启动窗口，更像大电流转向时底盘侧被拉垮——其中一次恢复后
固件报回的编码器计数从 `-2776` 回到 `-86`，而路线程序从不调用 `reset_encoder`。这需要
示波器在"70+ 速度原地转向 + 机械臂同时动作"时测轨压，软件修不了。
